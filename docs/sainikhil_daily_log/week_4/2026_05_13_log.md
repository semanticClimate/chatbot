### Detailed Error Breakdown and Solutions

Today I focused on debugging two major deployment issues with our dual-tunnel Cloudflare setup.

#### 1. The Iframe "Unsafe attempt to load URL" Error
**The Problem:** The Web UI and the API are served on two different `.trycloudflare.com` domains. When the Web UI tries to load the student book from the API inside an `<iframe>`, Cloudflare intercepts it to show its "Phishing Warning" page. Because they are on different domains, the browser's security sandbox blocks this warning page from loading, breaking the iframe completely.

**The Solution:** Since we cannot programmatically bypass the Cloudflare warning for cross-origin iframes, I updated the frontend to gracefully detect the block and prompt the user to authorize it.

**Code Change (`web_client/js/main.js`):**
Added an automatic health check during UI initialization:
```javascript
  apiInput.value = await resolveInitialApiBase(statusLine);
  await syncBookPanel(apiInput.value.trim(), statusLine);

  // Check if Cloudflare is blocking the API
  const checkApi = apiInput.value.trim();
  if (checkApi && isRemoteWebOrigin() && checkApi.includes("trycloudflare.com")) {
    getHealth(checkApi).catch(() => {
      statusLine.innerHTML = `⚠️ API blocked by Cloudflare warning. <a href="${checkApi}" target="_blank" style="color:inherit;text-decoration:underline;">Click here to authorize</a>, click "I Agree", then reload this page.`;
      statusLine.dataset.kind = "error";
    });
  }
```
Now, if the iframe is blocked, a clear link appears. Clicking it opens the API in a new tab where I can click "I Agree", and upon reloading, the iframe works perfectly!

#### 2. The 404 / ERR_NAME_NOT_RESOLVED Error on Restart
**The Problem:** Whenever I stopped and restarted the tunnels, Cloudflare generated brand new URLs. However, the Web UI kept trying to connect to the *old* API URL from the previous session (which it remembered in the browser's `localStorage`), resulting in a dead connection.

**The Solution:** The PowerShell startup script was missing a step to save the newly generated API URL (unlike the bash version). I updated the script to write the new API URL to `tunnel-api-base.txt`, which the Web UI automatically reads on startup.

**Code Change (`docs/installation/start-quick-tunnel.ps1`):**
First, clear the old file at the beginning of the script:
```powershell
# Clear stale API URL hint
Remove-Item -Path (Join-Path $RepoRoot "web_client\tunnel-api-base.txt") -Force -ErrorAction SilentlyContinue
```

Then, save the new URL once it's successfully generated:
```powershell
} else {
    # Save the new API URL for the Web UI to read
    $WebTunnelHint = Join-Path $RepoRoot "web_client\tunnel-api-base.txt"
    Set-Content -Path $WebTunnelHint -Value $ApiPublic

    Write-Host "Team B should open: $WebPublic"
    Write-Host "API base URL defaults to: $ApiPublic (served as web_client/tunnel-api-base.txt)"
}
```
With these changes, the UI automatically stays in sync with the active tunnel on every restart.
