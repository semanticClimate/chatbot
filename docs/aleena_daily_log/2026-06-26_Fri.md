# IPCC Climate Chatbot - Progress Brief (First Attempt)
> As of 26<sup>th</sup> June 2026

## What we were building
A chatbot that answers questions about the IPCC AR6 Synthesis Report. You ask a question, it searches the actual report, finds the most relevant passages, and gives a grounded answer with citations like [2.1.1].

## What we built
### 1. Data pipeline
Took the IPCC report in HTML format and wrote a parser that extracts all 222 paragraphs with their section metadata. Fixed a bug where the HTML itself had duplicate IDs that was causing the database to reject the data. Split paragraphs into 224 chunks, embedded them using a local AI model (MiniLM), and stored everything in ChromaDB. Verified it worked. asking "how much has global temperature risen?" correctly returned section 2.1.1 with high confidence.
### 2. Backend API
Built a Flask API with endpoints for sending questions, polling for answers, and managing sessions. Set up Celery as a background task runner and Redis as the message broker. Built the full RAG pipeline: question → rewrite if follow-up → retrieve relevant chunks → build prompt → call Ollama (Llama 3.2 running locally) → parse citations → return answer. Also built query rewriting so follow-up questions like "what about that?" get rewritten into full standalone queries before searching.
### 3. LLM
Used Ollama running locally with Llama 3.2. no API keys needed for development. AWS Bedrock wired in as a future production option.

## Where things stood
Everything was built and running individually. ChromaDB had all 224 chunks. Ollama was running. Redis was running. The Flask server and Celery worker both started. The retrieval pipeline was verified working.
The final blocker was a configuration issue where Flask and Celery weren't sharing the same Redis connection. Flask was trying to connect via the wrong protocol when firing background tasks. It was one environment variable loading fix away from working end to end.
The frontend had not been started yet.

## Why it was discarded
Despite solid progress, working with this stack on Windows proved consistently painful. Redis required a third-party Windows port. Celery has known issues on Windows requiring workarounds. Environment variables weren't loading in the right order across processes. Each fix revealed another layer of configuration friction.
The tech stack - Flask, Celery, Redis, ChromaDB, Ollama, MiniLM, all running as separate processes, was simply too heavy for local development. Too many moving parts, too many things that could go wrong independently, and too much time spent on infrastructure instead of the actual chatbot. It was eventually discarded in favour of a simpler approach.
