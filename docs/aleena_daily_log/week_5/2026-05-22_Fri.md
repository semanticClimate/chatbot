# May 22, 2026

## Context

Over the past few days (May 19–21), I had been investigating an issue where images inside the Climate Academy Student Book were not rendering correctly in the browser. Although the chatbot itself was functioning, diagrams and illustrations embedded within the book either failed to load or displayed broken image placeholders.

I initially suspected that the issue was related to the HTML generation process or the browser itself. However, after multiple rounds of testing, comparing different versions of the generated HTML, and tracing the rendering pipeline, I determined that the problem originated from how image paths were being validated before being embedded into the page.

---

## Investigation (May 19–21)

During the investigation, I:

- Tested the application using different versions of the generated student book.
- Compared the original HTML with the annotated HTML produced by the encyclopedia pipeline.
- Verified whether the browser was requesting the correct image locations.
- Examined browser developer tools and observed repeated **404 Not Found** errors for book images.
- Traced how image paths were processed inside the application's image inlining functions.
- Identified that valid project images were being rejected during the path validation stage before they could be embedded into the HTML.

Although I was close to identifying the root cause, it took several iterations of debugging before I fully understood where the validation logic was preventing the images from loading correctly.

---

## What was implemented

After identifying the source of the problem, I modified the image inlining logic used by both the Streamlit application and the backend rendering module.

Instead of validating images only relative to the directory containing the generated HTML, the validation scope was expanded to the entire project root directory.

This allowed legitimate images stored inside the project's `input/media` folder to be processed correctly while still preventing files outside the project directory from being accessed.

The same change was applied consistently across both rendering implementations to ensure identical behaviour throughout the application.

---

## Additional work

Alongside the code changes, I documented both the issue and its resolution to make future debugging easier.

The documentation included:

- Root cause analysis.
- Investigation process.
- Explanation of why the images produced 404 errors.
- Details of the implemented solution.
- Verification steps confirming that the fix worked.

I also regenerated the annotated student book and updated the associated project assets after verifying that the images were rendering correctly.

---

## Result

The book images now render correctly throughout the application without producing **404 Not Found** errors.

The implemented solution preserves the existing security checks while allowing legitimate project resources to be loaded successfully.

This debugging exercise also gave me a much deeper understanding of the project's rendering pipeline, how annotated HTML is generated, and how local resources are processed before being displayed in the browser.
